## 🔴 ממצא 1 · לקוח יכול לקבוע את המחיר שבו יחויב

**חומרה:** גבוהה · **קטגוריה:** הרשאות / שלמות נתונים כספיים

### שרשרת התקיפה

**חוליה א — החוק מתיר כל שדה.** `database.rules.json:22`:

```
".write": "... || (users/<phone> exists && !data.exists()
           && newData.child('clientPhone').val() === <הטלפון שלו>
           && newData.child('stage').val() === '')"
```

אין רשימת שדות מותרים. לקוח מחובר יכול ליצור הזמנה עם **כל תוכן**, כל
עוד הטלפון שלו והשלב ריק.

**חוליה ב — נעילת המחיר מדלגת על עצמה.** `firebase-db.js:1461`:

```js
if(!order.pricesLockedAt){       // ← אם השדה כבר קיים, שום דבר מכאן לא רץ
  ...
  update.pricesLockedAt = Date.now();
  if(lockedItems.length) update.lockedItems = lockedItems;
}
```

`lgLockAndAdvance` הוא **הכותב היחיד** של `lockedItems` בכל המערכת
(אומת בסריקה). אם הלקוח כבר כתב `pricesLockedAt`, המחירים שלו שורדים.

**חוליה ג — החשבונית מחייבת לפי מה שנעול.**
`api/hashavshevet-invoice.js:111`:

```js
for (const li of (o.lockedItems || [])) {
  const ppm2 = Number(li.pricePerM2 || 0);
  ...
  lines.push({ ..., price: ppm2.toFixed(3) });
}
```

### התקיפה בפועל

הגדרות Firebase של דפדפן הן ציבוריות מעצם הגדרתן — זו הסיבה שהחוקים הם
הגבול. לקוח עם סיסמה תקינה יכול לפנות ישירות ל-REST API של Firebase, בלי
לעבור דרך הפורטל:

```
PUT https://<db>.firebasedatabase.app/orders/sub_9999.json?auth=<הטוקן שלו>

{ "clientPhone": "<הטלפון שלו>", "stage": "",
  "orderClient": "...", "items": [...],
  "pricesLockedAt": 1,
  "lockedItems": [{ "sku": "8SMH", "area": 1, "quantity": 1,
                    "pricePerM2": 0.001, "lineTotal": 1 }] }
```

ההזמנה נכנסת לתור כרגיל, עוברת את כל התהליך, ובסוף **החשבונית שנשלחת
לחשבשבת נושאת את המחיר שהלקוח קבע.**

**מה מצמצם:** הבדיקה `if (!(ppm2 > 0))` מדלגת על שורה במחיר 0, ולכן אי
אפשר לחייב באפס. `0.001` עובר. בנוסף `totalFinal` מוצג במסכי האדמין,
כך שסכום חריג **עשוי** להתגלות — אבל בחשבונית מרוכזת של 20 הזמנות
בסוף חודש, קל מאוד לפספס.

### התיקון

רשימת שדות אסורים בחוק, על הזמנה שלקוח יוצר. ב-`database.rules.json`,
בתוך `orders/$orderId`, הוסף לתנאי הכתיבה של הלקוח:

```
&& !newData.hasChild('pricesLockedAt')
&& !newData.hasChild('lockedItems')
&& !newData.hasChild('totalFinal')
&& !newData.hasChild('hashavshevetInvoice')
&& !newData.hasChild('isTest')
&& !newData.hasChild('monthlyBilling')
&& !newData.hasChild('paymentStatus')
&& !newData.hasChild('readyStatus')
```

⚠️ **`paymentStatus` נכתב היום על ידי `saveSubmission` מהדפדפן של הלקוח**
(`firebase-db.js:460`). לפני החלת החוק צריך להסיר אותו משם, אחרת כל
העלאה תיכשל. שאר השדות אינם נשלחים מהפורטל ולכן בטוחים לחסימה מיידית.

⚠️ **Vercel לא מפרסם חוקי Firebase.** אחרי השינוי:
`node scripts/deploy-rules.js`

## 🟠 ממצא 2 · לקוח יכול לסמן הזמנה כפיקטיבית או כשוטף 30

**חומרה:** בינונית · **אותו שורש כמו ממצא 1**

**`isTest: true`** — `api/hashavshevet-invoice.js` מדלג על הקריאה
לחשבשבת ורושם חשבונית מדומה:

```js
if (isTest) { wgRes = { status: 200, ok: true }; text = ... simulated ... }
```

התוצאה: סחורה יוצאת, המערכת רושמת שחויבה, **ובחשבשבת אין מסמך**.

*מה מצמצם:* התצוגה המקדימה אומרת במפורש שההזמנה פיקטיבית, והרישום נושא
`simulated`. אדמין שקורא את המסך יראה. אדמין שלוחץ מהר לא.

**`monthlyBilling: true`** — `workday.html:695` (`_orderIsMonthly`) קורא
את הדגל מההזמנה עצמה, והדגל שעל ההזמנה גובר על רשומת הלקוח. סיום הובלה
מדלג על שאלת החשבונית בשקט.

**התיקון:** אותה רשימת שדות אסורים מממצא 1.

## 🟠 ממצא 3 · כל משתמש מחובר יכול לקפוץ את מונה ההזמנות

**חומרה:** בינונית · **קטגוריה:** שלמות נתונים

`database.rules.json:76-79`:

```json
"orderCounter": {
  ".write": "auth != null && ... root.child('users').child(<phone>).exists()",
  ".validate": "newData.isNumber() && (!data.exists() || newData.val() > data.val())"
}
```

הכתיבה פתוחה לכל משתמש שקיים ב-`users/` — כולל כל לקוח. זה **נדרש**, כי
הפורטל מושך מספר הזמנה בעת העלאה. ה-`.validate` מבטיח רק שהמספר עולה.

לקוח יכול לקבוע `999999999`. מכאן:
- כל ההזמנות מקבלות מספרים חסרי משמעות
- `toReference` ב-`hashavshevet-invoice.js:62` דוחה יותר מ-9 ספרות →
  **הפקת חשבוניות נשברת לכולם**
- המונה מונוטוני, ולכן **אי אפשר להחזיר אותו אחורה** בלי כתיבה ידנית

**התיקון המומלץ:** להעביר את משיכת המספר לנקודת API בצד השרת, שמשתמשת
ב-Admin SDK ועוקפת את החוקים. הלקוח מבקש מספר, לא כותב אותו.

**תיקון ביניים זול:** להוסיף תקרה לקפיצה:
`newData.val() > data.val() && newData.val() < data.val() + 1000`

## 🟡 ממצא 4 · חשבון Auth יתום ללא אימייל

`uid=0548000775`, כניסה אחרונה 4.8.2026, **ללא כתובת אימייל**, ואין לו
רשומה ב-`users/`. לאותו לקוח יש חשבון שני ותקין
(`0548000775@luzglass.local`).

**מה הוא יכול לעשות: כלום.** כל חוק דורש `auth.token.email != null`,
ו-`verifyAdmin` מחזיר 403 `token has no usable identity`. אומת בקוד.

**התיקון:** מחיקה. חשבון שיכול להתחבר ולא אמור להתקיים הוא בלבול מיותר
בביקורת הבאה.

## 🟡 ממצא 5 · `meta/invoiceCounter` בלי הגנת מונוטוניות

`orderCounter` ו-`chisumCounter` שניהם נושאים
`.validate: newData.val() > data.val()`. `invoiceCounter` — לא.

הכתיבה אליו מוגבלת לאדמין, ו-API החשבוניות משתמש ב-Admin SDK שעוקף חוקים
ממילא, ולכן **שום דבר לא שבור היום**. אבל כתיבה ידנית שתחזיר את המונה
אחורה תייצר **אסמכתאות כפולות על מסמכי הנהלת חשבונות אמיתיים**.

**התיקון:** להוסיף את אותו `.validate` שיש לשני האחרים.
